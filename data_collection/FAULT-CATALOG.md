# 故障清单与定位手册(Fault Catalog)v1

> **配套**:[[DATA-COLLECTION-SPEC]](规格)· 本文件是**台架上用的清单**
> **每条故障的四段结构**:`怎么注入` → `会看到什么(逐层)` → `在哪里定位` → `会和什么混淆`

---

## 0. 先回答:定向采集,还是采完筛选?

**两者不是二选一,筛选是定向采集的一个必经阶段。** 完整流水线是四步:

```
① 定向注入   施加已知扰动,层标签由装置给出        ← 标签的唯一来源
② 采集       .drm + 副档 + 注入日志
③ 筛选核验   跑 detector battery                  ← 不做这步就会有 implicit B
   ├─ 预期症状出现了吗?          否 → valid: false,作废
   └─ 有没有出现别的现象?        有 → 登记为 known_confound,不作废
④ 成 case    才写进 GT
```

⚠️ **③ 不可省。** 定向注入不做事后筛选,正是 implicit B 的标准产生方式 ——
你以为注入了 A,实际数据里是 A+B,而标签只写了 A。

### 0.1 三种采集方式,各自能产出什么

| 方式 | 标签来源 | **完备性** | 产出层级 | 成本 |
|---|---|---|---|---|
| **完全定向**(注入 + 核验) | 实验装置 | **完备** | T1 / T2 | 高,需台架 |
| **半定向**(制造条件,不精确控制) | 现场记录 + 核验 | 部分完备 | T1(降级)/ T3 | 中 |
| **纯筛选**(扫已有/自然数据) | detector 检出 | 🔴 **构造上不完备** | **仅 T3** | 低,可无限规模 |

> **纯筛选永远给不出完备标签** —— 因为"没检出"不等于"不存在"(T3 可观测性不对称)。
> 所以 **T1/T2 必须定向,不能靠筛选替代**;而 T3 必须靠筛选,因为真实故障无法预约。

### 0.2 哪些故障**无法**定向?

| 故障 | 为什么不能定向 | 归宿 |
|---|---|---|
| 真实规模的网络拥塞 | 造不出几百个真实用户 | 仅 T3 |
| 硬件老化 / 扇区接反 | 不能真的去拆基站 | 仅 T3(或需运营商配合) |
| 外部干扰源 | 不可控、不可预约 | 仅 T3 |
| 核心网侧故障 | 需要核心网权限 | 视权限 |

⇒ **清单里每条都标了"可定向"三档:✅ 可 / 🟡 需基站或服务器权限 / ❌ 只能筛选。**

## 1. 一个完整的例子 —— 从注入到 GT,走完全程

**故障:F-01 覆盖空洞,workload = streaming**

### ① 注入(操作员做什么)

```
09:14:22.000  衰减器 0 dB
09:14:22.000  开始 ramp:0 → 25 dB,斜率 50 dB/s(用时 500 ms)
09:14:22.500  保持 25 dB
09:14:27.500  ramp 回 0 dB(500 ms)
09:14:28.000  恢复,等待 5 min 再做下一次
```

写进 `injection_log.yaml`:

```yaml
- seq: 7
  t_start: 2026-09-15T09:14:22.000Z
  t_end:   2026-09-15T09:14:27.500Z
  layer: RF                      # ⭐ 这一行就是 primary_attribution
  mechanism: coverage_hole
  params: {attenuation_db: 25, ramp_ms: 500, hold_ms: 5000}
  condition: A_only
  workload: streaming
  expected_symptom: rebuffer
  observed_symptom: rebuffer     # 现场目视
  valid: true
```

### ② 会看到什么(逐层,这就是"结果")

| 层 | 现象 | 量级(预期) | 延迟 |
|---|---|---|---|
| **RF** | RSRP 下降 | **≈ −25 dB**(与衰减量近似 1:1) | 即时 |
| **RF** | SINR 下降 | 5–15 dB(取决于噪声底) | 即时 |
| **MAC** | MCS 降档、PRB 分配变化、HARQ 重传率上升 | MCS 下 5–10 档 | ~10–100 ms |
| **RLC** | 重传上升;若够深则丢弃 | — | ~100 ms |
| **RRC** | 若跌破门限:测量报告 → 切换;若 > T310:RLF | — | ~几百 ms |
| **Transport** | 吞吐下降、RTT 上升、TCP 重传 | 吞吐降 50–90% | ~200 ms–1 s |
| **App** | ⭐ **后果取决于 workload** | 见下 | 1–10 s |

⭐ **N3 就在最后一行**:同一个 25 dB 衰减 5 秒 ——

| workload | App 层后果 |
|---|---|
| **ping** | 几个包 RTT 升高或丢失。**几乎无影响** |
| **iperf(TCP)** | 拥塞窗口坍塌,恢复需数秒。**影响远长于故障本身** |
| **streaming** | 缓冲区吸收 → **可能完全无感**;若缓冲不足 → rebuffer |
| **teleop** | 🔴 **控制环立即超时**。缓冲不能救,因为 teleop 不能靠缓冲 |

> **这张表就是 N3 的论证**:同一个物理故障,后果跨 workload 相差一个数量级。
> **而这正是现有 15 条 ping 数据完全看不出来的东西。**

### ③ 在哪里定位

| 通道 | 做法 |
|---|---|
| **XCAP GUI** | Graph tab 打开 RSRP / SINR / 吞吐 三条曲线叠加,时间轴对齐到 09:14:22 |
| **XCAP 内建** | `Message Duration Time Analysis` 量中断时长;若触发切换则查信令 |
| **离线 detector** | `d_rsrp_drop`:滑窗内 RSRP 相对该 trace 自身基线下降 > 10 dB 且持续 > 1 s |
| **交叉校验** | 注入日志的墙钟 ↔ trace 时钟(**偏差表在试采时标定**) |

### ④ 产出的 GT

```yaml
task_id: STREAM-COV-007
tier: T1                                    # 单故障,标签完备
model:
  source_logs: [20260915-lab-A-s03-run07.drm]
  viewer_mode: message
  multi_process: false
analysis_config:
  sampling_rate: "All"                      # 采最细,分析时可降
  filters: []
  canonical_clock: TIME_STAMP
symptom: {type: rebuffer, t: <trace时间>, duration_ms: 2300}
causal_chain:
  - {level: 4, layer: APP,       claim: "播放缓冲耗尽",              verifier: chk_rebuffer}
  - {level: 3, layer: TRANSPORT, claim: "吞吐由 12 Mbps 降至 1.4 Mbps", verifier: chk_tput}
  - {level: 2, layer: MAC,       claim: "MCS 由 22 降至 6",           verifier: chk_mcs}
  - {level: 1, layer: RF,        claim: "RSRP 由 −92 降至 −117 dBm",   verifier: chk_rsrp}
primary_attribution: {level: 1, layer: RF, mechanism: coverage_hole}
answer_scope: "归因到 layer + mechanism"
injection_ref: {session: 20260915-lab-A-s03, seq: 7}    # ⭐ 标签的物理凭据
known_confounds:
  - {phenomenon: "HARQ 重传率上升", layer: MAC, relation: consequence_of_primary, grading: partial}
  - {phenomenon: "TCP 重传突发",    layer: TRANSPORT, relation: consequence_of_primary, grading: partial}
fault_multiplicity: single                  # 定向 + 核验 ⇒ 可以写 single
detector_coverage: [d01..d24]
```

⚠️ 注意 `fault_multiplicity`:**只有定向注入 + 全 detector 核验通过,才能写 `single`**。
筛选出来的一律写 `single_detected`。

## 2. 故障清单

**图例**:可定向 ✅ 直接可做 / 🟡 需基站或服务器权限 / ❌ 只能筛选
**优先级**:P0 必采 / P1 应采 / P2 有余力再采

---

### RF / PHY 层

#### F-01 覆盖空洞(Coverage Hole)· ✅ · **P0**
| | |
|---|---|
| **注入** | 步进衰减器,`0 → N dB`,ramp 500 ms,保持 T 秒,回 0 |
| **参数网格** | N ∈ {10, 20, 25, 30} dB;T ∈ {1, 5, 15} s |
| **逐层后果** | RSRP −N dB → SINR 降 → MCS 降档 → 吞吐降 → App(见 §1②) |
| **XCAP 定位** | Graph:RSRP / RSRQ / SINR;Map:覆盖着色 |
| **离线 detector** | RSRP 相对自身基线跌 > 10 dB 且持续 > 1 s |
| **易混淆** | ⚠️ 与 **F-02 干扰**:两者都压 SINR。**判别:干扰时 RSRP 不变而 SINR 降;覆盖空洞时两者同降** ← **这一对是 N1 混淆矩阵的核心对照** |
| **注意** | N 太大会直接触发 RLF(变成 F-07),做 N 的梯度时要记录**从哪一档开始变成 RLF** |

#### F-02 同频干扰(Co-channel Interference)· ✅ · **P0**
| | |
|---|---|
| **注入** | 信号源在服务小区频点注入受控干扰;或开同频邻区 |
| **参数网格** | 干扰功率使 SINR 降 {5, 10, 15} dB;带宽 {部分 RB, 全带宽} |
| **逐层后果** | **RSRP 基本不变**,SINR 降 → BLER 升 → HARQ 重传 → MCS 降 → 吞吐降 |
| **XCAP 定位** | Graph:SINR / RSRQ / BLER;⭐ 内建 `PSYNC / PSC Pollution Analysis` |
| **离线 detector** | SINR 跌 > 5 dB **而 RSRP 变化 < 2 dB** |
| **易混淆** | F-01(见上)、F-04(MIMO 降秩也压吞吐但 SINR 不一定降) |
| ⭐ **解锁** | **这条能让内建的 PSC Pollution Analysis 第一次有数据可跑** —— 现有数据完全没有 |

#### F-03 快衰落 / 多径 · 🟡(需衰落仪) · P2
| | |
|---|---|
| **注入** | 衰落仪设定 EPA/EVA/ETU 信道模型 + 多普勒 |
| **逐层后果** | SINR 高频波动、CQI 抖动、MCS 频繁切换、吞吐不稳 |
| **离线 detector** | SINR 的**方差**升高而**均值**不变 ← 与 F-01/F-02 的判别点 |
| **备注** | 没有衰落仪就跳过,不是必需 |

#### F-04 天线支路失效(MIMO 降秩)· ✅ · **P1**
| | |
|---|---|
| **注入** | **物理断开一路天线**,或该路加 40 dB 衰减 |
| **逐层后果** | Rank Indicator 由 2 降为 1 → 峰值吞吐**腰斩**,而 RSRP/SINR **几乎不变** |
| **XCAP 定位** | Graph:Rank Indicator / 层数 / PMI;吞吐曲线 |
| **离线 detector** | RI 分布由双峰变单峰,且吞吐上限减半 |
| **易混淆** | ⚠️ **吞吐掉一半但 RF 指标正常** —— 极易被误判为 Transport 或 MAC 层问题。**这是 N1 最有价值的一类样本** |
| ⭐ | 物理上最干净的注入之一:一个动作,后果明确,且**症状与层的直觉不符** |

---

### RRC / 移动性 层

#### F-05 切换中断(Handover Interruption)· ✅ · **P0**
| | |
|---|---|
| **注入** | **两条 RF 通路的衰减器反向互换**("虚拟行驶"):A 路 0→30 dB 的同时 B 路 30→0 dB |
| **参数网格** | 交叉斜率 {快 10 dB/s, 慢 2 dB/s};是否在交叉点制造重叠不足 |
| **逐层后果** | 测量报告 → RRC Reconfiguration → **中断 gap** → 上行/下行空档 → TCP 超时 / 控制环超时 |
| **XCAP 定位** | ⭐ **内建 `Message Duration Time Analysis` 直接量中断时长**(两条消息之间的时间差,官方按 Chipset Time 算);信令流窗口看 RRC 序列 |
| **离线 detector** | RRC Reconfiguration ↔ Reconfiguration Complete 的时间差 > 阈值;同期数据面出现 gap |
| **易混淆** | F-01(切换前必然伴随 RSRP 下降 —— **这正是 T2 组合的天然素材**) |
| ⭐ | **中断时长是连续量,可以做成 L2 计算题、L4 对比题、L5 归因题三种** |

#### F-06 乒乓切换(Ping-pong)· ✅ · P1
| | |
|---|---|
| **注入** | 让两路衰减在切换门限附近**来回振荡**(±2 dB,周期 2 s) |
| **逐层后果** | 短时间内多次切换 → 累计中断时间 → 吞吐持续劣化 |
| **离线 detector** | 单位时间内切换次数 > 阈值,且回切比例高 |
| **易混淆** | 与"移动性正常"的边界模糊 —— **门限本身就是配置**,这条天然带 T5 味道 |

#### F-07 无线链路失败(RLF)· ✅ · **P0**
| | |
|---|---|
| **注入** | 深度衰减(如 40 dB)并保持 **> T310** |
| **参数** | 必须记录基站的 **T310 / N310 / N311** 配置值 |
| **逐层后果** | RLF → RRC 重建 或 掉线 → 上层全断 |
| **XCAP 定位** | 信令流;计数器 `num_rlf_issued` / `last_rlf` |
| ⚠️ **陷阱** | 🔴 **`num_rlf_issued` 是累计计数器,不是事件**(T7)。"此刻读到 279" ≠ "此刻发生 279 次"。**真正的事件是相邻采样的差分** —— 而 XCAP 的 `.dat` 层可能已经差分过(P18),**两层语义相反** |
| **易混淆** | 与 F-05 切换失败的边界:失败的切换可能以 RLF 收场 |

#### F-08 邻区漏配(Missing Neighbor)· 🟡 需基站权限 · **P1**
| | |
|---|---|
| **注入** | 从服务小区的邻区列表中**删掉**目标小区,再走一次 F-05 的流程 |
| **逐层后果** | 该切走而切不走 → 停留在劣化小区 → 吞吐劣化 → 最终 RLF |
| **XCAP 定位** | ⭐ **内建 `Finding Missing Neighbors`** |
| ⭐ **解锁** | **这条让内建的 Finding Missing Neighbors 第一次有数据可跑** |
| **为什么重要** | 这是**配置类根因**,与物理类根因(F-01/02)在证据形态上完全不同 —— **agent 要学会两种不同的推理** |

### MAC / 调度 层

#### F-09 PRB 拥塞 · ✅ · **P0**
| | |
|---|---|
| **注入** | 同小区加 **N 个负载 UE**(各跑满速 iperf),被测 UE 与之竞争 |
| **参数网格** | N ∈ {1, 3, 6};负载 UE 速率 {尽力, 限速} |
| **逐层后果** | 被测 UE 的 PRB 分配下降 → 吞吐下降,而 **RF 指标完全正常** |
| **XCAP 定位** | ⭐ 内建 **`LTE RB Scheduling Map`**;**`LTE DCI Analysis`**(逐 TTI) |
| ⚠️ **陷阱** | 🔴 **DCI Analysis 的结果窗口不保存、不可重开**(厂商文档明写)⇒ **该通路是一次性的,不能当可复现 oracle**;且需先跑昂贵的 `Reprocess` |
| **离线 detector** | PRB 分配数下降 > 50% 而 RSRP/SINR 变化 < 2 dB |
| **易混淆** | ⚠️ **与 F-04(MIMO 降秩)、F-12(Transport 限速)三者症状高度相似 —— 都是"吞吐掉了但 RF 正常"。这三条构成 N1 混淆矩阵最难的一组** |

#### F-10 调度优先级 / 不公平 · 🟡 需基站权限 · P2
| | |
|---|---|
| **注入** | 改调度器策略或 QoS 优先级 |
| **备注** | 与 F-09 后果相近但根因在配置,若有基站权限值得做 |

### RLC / PDCP 层

> 🔴 **重要提醒**:RLC/PDCP 在真实场景中**多数是后果而非根因**。
> 若不能改基站配置,**这一层无法成为 `primary_attribution`**,
> 混淆矩阵会从 5×5 退化为 4×4 —— **见 §3**。

#### F-11 RLC 重传门限 / PDCP 重排序超时 · 🟡 需基站权限 · P1
| | |
|---|---|
| **注入** | 调小 `maxRetxThreshold`,或把 PDCP 重排序定时器设得过短 |
| **逐层后果** | 正常的乱序被当成丢失 → 不必要的丢弃 → 上层吞吐劣化,而 **RF 与 PRB 都正常** |
| **XCAP 定位** | RLC DL 丢包表:`Drpped_Total` / `Status_PDU_Drop` / `Dropped_By_FlowControl` |
| ⚠️ **陷阱** | 🔴 现有数据里 `Drpped_Total` **最大只有 13**,`Status_PDU_Drop` **全 0**,`Dropped_By_FlowControl` **是空表** —— **注入后必须先确认这些表真的被填充**,否则这条无法验证 |
| **备注** | ⭐ 若拿不到基站权限,**这一层就没有根因样本**,必须在论文里说明 |

### Transport 层

#### F-12 带宽限制 · ✅ · **P0**
| | |
|---|---|
| **注入** | 核心网侧 `tc qdisc … rate` 限速 |
| **参数网格** | 限到 {50%, 20%, 5%} 的基线吞吐 |
| **逐层后果** | 吞吐降,**而 RF、PRB、RLC 全部正常** |
| **XCAP 定位** | 🔴 **需要抓包副档**(`.drmp`/`.drmmp`/`.drmw`),否则 Transport 层看不到 |
| **易混淆** | ⚠️ 与 F-09、F-04 同组 —— 见 F-09 |
| ⭐ | **这条是"注入层 = 标签层"原则最干净的演示**:物理层完全正常,根因在传输层 |

#### F-13 时延 / 抖动 · ✅ · **P0**
| | |
|---|---|
| **注入** | `netem delay <mean> <jitter> distribution normal` |
| **参数网格** | 均值 {50, 150, 300} ms;抖动 {10, 50} ms |
| **逐层后果** | RTT 升 → TCP 吞吐降(BDP)→ **teleop 控制环直接超时** |
| ⭐ **N3** | **同一个 150 ms 时延**:ping 只是数字变大;streaming 几乎无感;**teleop 崩溃**。这是 N3 最干净的一条 |
| **XCAP 定位** | Ping/Iperf 事件表(⚠️ **这几张表的 `ChipTime` 比无线层差 5 小时**,见 B2);抓包副档 |

#### F-14 丢包 · ✅ · **P0**
| | |
|---|---|
| **注入** | `netem loss <p>%`,分**随机**与**突发**两种模型 |
| **参数网格** | p ∈ {0.5, 2, 5}%;model ∈ {random, burst} |
| **逐层后果** | TCP 重传与拥塞窗口坍塌;UDP/teleop 直接丢帧 |
| **易混淆** | ⚠️ **与 F-01/F-05 造成的空口丢失极难区分** —— 判别只能靠"RF 是否正常"。**这一对是跨层混淆的核心样本** |
| ⭐ | **随机 vs 突发**两种模型后果差别很大,而根因标签相同 —— 可做成 L5 的细分归因题 |

### App / 服务器 层

#### F-15 服务器端限速或抖动 · ✅(需控制服务端) · P1
| | |
|---|---|
| **注入** | 在流媒体/遥操作服务端限速或注入延迟 |
| **为什么要做** | ⭐ **提供"根因不在网络里"的样本** —— 没有这类样本,agent 会学会"总能在无线侧找到原因",假阳性率无法测量 |
| **易混淆** | 与 F-12/F-13 症状几乎相同,判别靠端到端分段测量 |

## 3. 🔴 可归因的层数,取决于你能控制多少网络

| 你能控制 | 可作 `primary_attribution` 的层 | 混淆矩阵 | 每层 n(总数 150) |
|---|---|---|---|
| **仅 RF 通路 + 传输链路** | RF、RRC、Transport(3 层) | **3×3** | 50 |
| **+ 负载 UE** | 上述 + MAC(4 层) | **4×4** | 38 |
| **+ 基站配置权限** | 上述 + RLC/PDCP(5 层) | **5×5** ✅ | **30** |

⚠️ **§2.1 里"5 层 × 30"的算式,前提是有基站配置权限。**
若拿不到,混淆矩阵退化为 4×4,**N1 的论证强度下降但仍成立**;
届时应把节省的采集量转投 T2 组合层。

🙋 **这是排期前必须回答的问题:我们对基站有配置权限吗?**

## 4. T2 组合怎么选 —— 挑"最容易混淆"的配对

组合不是随便配。**优先选那些单独出现时容易被混淆的对**,因为组合后能测出 agent 是否会在混淆中失去分辨力。

| 组合 | 为什么选它 | 优先级 |
|---|---|---|
| **F-01 + F-12**(覆盖空洞 + 传输限速) | 两个都让吞吐降,**一个在最底层一个在中层**。测能否分离跨层共因 | **P0** |
| **F-02 + F-09**(干扰 + PRB 拥塞) | 都压有效速率,**RF 指标一降一不降**。测判别依据是否稳固 | **P0** |
| **F-05 + F-14**(切换 + 丢包) | 切换本身会造成丢包 —— **注入的丢包能否与切换自带的丢包分开?** | **P0** |
| **F-04 + F-09**(MIMO 降秩 + 拥塞) | 两者 RF 都正常、都压吞吐。**最难的一组** | P1 |
| **F-01 + F-13**(覆盖 + 时延) | 一个空口一个传输,**对 teleop 后果叠加还是相乘?** | P1 |
| **F-08 + F-01**(漏配 + 覆盖) | 配置类 + 物理类,**证据形态完全不同** | P1 |

每组跑 `sham / A / B / A+B` 四条件 × 3 次。**②③ 与 T1 复用,增量只有 ①④。**

## 5. 采集优先级(若时间不够,按此顺序砍)

| 档 | 故障 | 理由 |
|---|---|---|
| **必采 P0** | F-01, F-02, F-05, F-07, F-09, F-12, F-13, F-14 | 覆盖 4 个层,构成混淆矩阵主体,全部可定向 |
| **应采 P1** | F-04, F-06, F-08, F-11, F-15 | F-04/F-08 提供"反直觉"样本;F-15 提供网络外根因;F-11 是 RLC 层唯一来源 |
| **有余力 P2** | F-03, F-10 | 需要额外设备或权限 |

⭐ **P0 八条 × 3 workload × 6 重复 = 144 个 case**,已经满足 §2.1 的量。
**P1 是提升论证质量的,不是凑数的。**

## 6. 试采选哪两个?

按 [[DATA-COLLECTION-SPEC]] §7,试采是 `3 workload × 2 机制 × 3 重复`。**建议选:**

| 选择 | 理由 |
|---|---|
| **F-01 覆盖空洞** | 最简单、最可控、后果最明确。**若这条都验不通,后面全部免谈** |
| **F-13 时延抖动** | 注入在**另一端**(传输侧),与 F-01 构成跨层对照;⭐ 且它的 N3 效应最戏剧(ping 无感 / teleop 崩溃) |
| **组合 = F-01 + F-13** | 一个空口 + 一个传输,**是 §4 里 P1 的那一组**。测"跨层双故障能否分离" |

**这两条还能顺带回答两个基础设施问题**:F-01 验证 RF 侧注入链路与对时;F-13 验证抓包副档是否真的让 Transport 层可见(收 A3)。
