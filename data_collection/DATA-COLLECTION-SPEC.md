## 1. 🔴 先解决一个概念问题:单故障 vs 多故障

**提问**:benchmark 要求单一 error,但真实情况往往是 multiple error。这个 gap 要不要考虑?

**回答**:要,而且**它不是要被消除的缺陷,是要被测量的现象**。理由如下。

### 1.1 三种"多重性"必须分开,它们的处理方式完全不同

| | 名称 | 形态 | 例子 | 处理 |
|---|---|---|---|---|
| **M-A** | **因果链多重性**(纵向) | 单一根因,多个层级都"是"原因 | rebuffer ← 吞吐骤降 ← SINR 恶化 ← 覆盖空洞 | ✅ **已解决** —— GT schema 的 `causal_chain` 逐级记录,`answer_scope` 规定答到哪一级。见 T2 |
| **M-B** | **并发独立故障**(横向,可分离) | 两个互不相干的问题同时存在,各有各的症状 | 覆盖空洞 + 邻区列表配错 | 🟡 **按症状切题**即可分离,见 §1.2 |
| **M-C** | **交互 / 共因故障**(横向,纠缠) | 两个故障的后果互相影响,或有一个隐藏共因产生两个表象 | 拥塞导致切换失败,切换失败又加剧拥塞 | 🔴 **不可分离。答案本身就是一个集合或一张图** |

⚠️ **此前的 T1(implicit B)只覆盖了 M-B 的一个特例**("瞄准 A 时意外混进 B")。
**M-C 是新的,而且它才是真实数据的常态。**

### 1.2 关键认识:单故障不是**数据**的性质,是**问题**的性质

同一份多故障 trace,可以问出单答案的题:

| 问法 | 答案数 |
|---|---|
| "**t=128.42 这一次** rebuffer 是什么造成的?" | 通常唯一(该症状实例有支配性的近因) |
| "这个网络有什么问题?" | 天然多解 |

⇒ **杠杆不在"净化数据",在"限定问题的作用域"** —— 这正是 GT schema 里 `answer_scope` 字段的用途,现在它的重要性要上调。

### 1.3 由此得到三层数据分层 —— **这是本规格的核心结构**

| 层 | 数据来源 | 标签形态 | **标签完备性** | 用途 |
|---|---|---|---|---|
| **T1 单故障注入** | 受控注入,一次一个机制 | 单一 `primary_attribution` | **正确且完备** | 消融、教学集、N1 混淆矩阵 |
| **T2 组合注入** | 受控注入,**故意同时注入 A 和 B** | 完整标签集 `{A, B}` + 交互效应 | ⭐ **唯一能拿到完备多故障标签的地方** | 测"多故障下能力如何退化" |
| **T3 真实混合** | 已有数据 + 新采集中自然发生的段 | **排序的因素列表** + 可核验证据 | **构造上不完备**(必须诚实承认) | 外部效度 |

⭐ **论文主张随之改变,而且变强了**:

> 不是 *"我们做了一个 RCA benchmark"*,而是
> **"我们测量了:当从单故障走向多故障时,agent 的 RCA 能力退化多少 —— 以及现有的单故障 benchmark 高估了多少。"**

**T1 → T2 → T3 的性能衰减曲线本身就是头条结果。** 若 agent 在 T1 上表现好、在 T3 上崩溃,这既是对 agent 的评价,**也是对整个 benchmark 建构实践的批评** —— 后者是 SIGCOMM 审稿人乐见的那类结论,而且它直接服务 N2(RCA ground-truth 效度)。

### 1.4 ⭐ T2 的设计:2×2 因子设计,测的是**交互效应**

同一场次内,对每一对机制 (A, B) 跑四种条件:

```
①  sham   —— 注入装置在位,但不施加(0 dB / netem 0ms)   → 阴性对照
②  A only —— 只注入 A                                    → A 的边际效应
③  B only —— 只注入 B                                    → B 的边际效应
④  A + B  —— 同时注入                                    → 联合效应
```

⇒ **`④ − (② + ③)` 就是交互项。** 这直接回答"多故障的后果是不是各故障后果之和",
而这**是一个真正的网络发现,不是 agent 发现** —— 它可以独立成为论文 §8 的一段,也可能成为 N3 的一部分。

⚠️ ① 的阴性对照**不可省**:如果 sham 条件下也检出"故障",说明基线本身不干净,该场次全部作废。

### 1.5 T3 的答案形态必须换

单一标签在多故障数据上不成立。T3 的答案改为:

```yaml
answer_form: ranked_factors
factors:
  - {rank: 1, layer: RRC,  mechanism: handover_interruption, weight: 主导,   evidence: [...]}
  - {rank: 2, layer: RF,   mechanism: interference,          weight: 加剧,   evidence: [...]}
  - {rank: 3, layer: MAC,  mechanism: prb_starvation,        weight: 伴随,   evidence: [...]}
completeness: incomplete        # 🔴 构造上不完备,不得声称穷尽
detector_coverage: [d01,d03,d07,...]   # 只对跑过的 detector 负责
```

> 母计划 §6 kill criteria 已有先例:*"专家分歧率极高 → 任务改为因素排序,N2 反而更强"*。
> **现在这不是止损方案,是 T3 的默认形态。**

## 2. 要采多少

### 2.1 反推:由 N1 混淆矩阵定下限

可归因的层实际是 **5 个**(RF/PHY、MAC、RLC/PDCP、RRC、Transport;App 层通常是**症状**不是根因)。

| n / 每层 | 二项标准误 | 能区分的准确率差 |
|---|---|---|
| 15 | ±0.12 | >35pp,太粗 |
| 25 | ±0.09 | ~25pp |
| **30** | **±0.084** | **~20pp** ✅ |

⇒ **5 层 × 30 = 150 个 T1 case。**

N3 的配对设计复用同一批:**8 种机制 × 3 种 workload × 6 次重复 = 144**,
映射到 5 个层后每层拿到 18–36 个。**两张图共用一批 case。**

**八种机制**:切换中断 / 覆盖空洞(RSRP) / 同频干扰(SINR) / PRB 拥塞 / RLF / 带宽限制 / 时延抖动 / 丢包。

### 2.2 时长

⚠️ **T1(implicit B)的直接约束:两次注入之间至少 5 分钟干净基线,机制绝不重叠。**
(T2 层是**故意**重叠,但那是设计,不是污染 —— 且标签完备。)

| 用途 | 算式 | 时长 |
|---|---|---|
| **T1 单故障主体** | 150 × 5 min | 12.5 h |
| **T2 组合注入**(增量) | 10 组合 × (④+① 两条件) × 3 重复 × 5 min<br>(②③ 与 T1 复用) | 5.0 h |
| 负例段 | 30 × 3 min | 1.5 h |
| 每种 workload 的干净基线(L1–L4 素材 + 变异母本) | 3 × 1 h | 3.0 h |
| **留出集**(异日 / 异机 / 异地) | | 5.0 h |
| 失败重跑冗余 | 注入部分 × 30% | 5.0 h |
| **合计** | | **≈ 32 h** |

⇒ 按 **30–35 小时**排期。

### 2.3 字节

实测锚点:**1.13 GB / 17 min(ping @1Sec)= 4.0 GB/h**。

| workload           | 估计         | 依据                          |
| ------------------ | ---------- | --------------------------- |
| ping / iperf + 抓包  | ~5 GB/h    | 实测 4 GB/h 打底                |
| **streaming + 抓包** | ~8–10 GB/h | 5 Mbps 码流单 IP 载荷即 2.25 GB/h |
| **teleop + 抓包**    | ~6–8 GB/h  | 码率低但包率高                     |

32 h × 均值 7 GB/h ⇒ **≈ 220 GB 原始 `.drm` + 副档**,规划按 **200–300 GB**。

**Model 展开系数未知**(⬜ 试采时实测),规划先按 1.5–3×;T5 实验要为同一份数据建 All / 1Sec 两套 Model,再乘一次。
⇒ **工作存储按 1 TB 备。这不是瓶颈。**

## 3. "受控"到底指什么 —— 注入装置与控制变量

### 3.1 ⭐ 第一原则:注入装置定义层标签

> **在哪一层施加扰动,`primary_attribution` 就是哪一层。**

这是 N1 混淆矩阵的 GT 来源,也是它可辩护的原因 —— 层标签**不是标注员的判断,是实验装置的物理事实**。

⚠️ 推论:**同一个症状必须能由不同层的注入产生**,否则混淆矩阵没有意义。
例:"吞吐下降"要能分别由 RF 衰减、PRB 拥塞、Transport 限速三条路径造成 —— **这三组必须都采**。

### 3.2 逐机制的注入方式与控制量

> ⭐ **完整的 15 条故障清单、逐层预期后果、XCAP 定位方式、易混淆对照、T2 组合选择与采集优先级,见 [[FAULT-CATALOG]]。**
> 下表是摘要;台架上用那一份。

| # | 机制 | **层** | 注入装置 | 必须记录的控制量 |
|---|---|---|---|---|
| 1 | **覆盖空洞 / RSRP 下降** | RF | **可编程步进衰减器**串在 RF 通路 | 衰减曲线(dB vs 时间)、**斜率**、保持时长、起止墙钟 |
| 2 | **同频干扰 / SINR 恶化** | RF | 信号源注入受控干扰(定功率/定带宽),或同频邻区 | 干扰功率、中心频率、带宽、调制、起止墙钟 |
| 3 | **切换中断** | RRC | **两条 RF 通路的衰减器互换**("虚拟行驶") | 两路衰减曲线、交叉点、切换门限(A3/A5 offset)、TTT |
| 4 | **RLF** | RRC | 深度衰减,跌破门限并保持 > T310 | 衰减深度、保持时长、**T310/N310 配置值** |
| 5 | **PRB 拥塞** | MAC | 同小区加负载 UE,或改基站调度配置 | 背景负载 UE 数、各自速率、调度器策略 |
| 6 | **带宽限制** | Transport | 核心网侧 `tc`/`netem` 限速 | 限速值、burst、队列长度 |
| 7 | **时延抖动** | Transport | `netem delay/jitter` | 均值、分布、相关性 |
| 8 | **丢包** | Transport | `netem loss` | 丢包率、模型(随机/突发) |

⭐ **① 优于"开车走到弱覆盖区"**:衰减器可重复、可精确定时、可逐 dB 复现;实地行驶不可重复,而**可重复性是 T2 因子设计的前提**。

### 3.3 必须固定并记录的变量

| 类别 | 变量 |
|---|---|
| **无线** | 小区功率、PCI、频点、带宽、邻区列表、切换门限(A3/A5 offset、TTT)、T310/N310 |
| **UE** | 型号、固件、**IMEI**、天线位置(**静止优先**;若行驶则记 GPS 路线)、锁频/锁制式设置 |
| **采集链** | XCAL 版本、**ICD 版本**、抓包开关、logging mask、采样设置 |
| **workload** | streaming:码率/编码/分辨率/缓冲区大小;teleop:控制环频率/包大小/协议;iperf:并发流数/拥塞控制算法 |
| **环境** | 场次时间、温度(室外)、背景负载 |

🔴 **ICD 版本必须记录并在整个 campaign 内保持一致**。
依据:官方 release note 带 `Supported ICD version` 表(5G QC = `FJ`,4G QC = `BE`),
**ICD 决定 diag 包怎么解**。混批 = `Ver=1.05` vs `1.11` 那个问题重演。

### 3.4 可重复性判据

| 判据 | 要求 |
|---|---|
| 每个注入条件重复 | **≥3 次** |
| 判定"复现"的标准 | ⚠️ **症状复现**,不是注入复现。施加了同样的衰减但没出现症状 = **该次作废并记录** |
| 阴性对照(sham) | **每场次至少 1 次**。sham 下检出故障 ⇒ **该场次全部作废** |
| **canary 段** | 每场次**首尾**各跑一段完全相同的 2 分钟脚本序列 |

> **canary 的作用**:检测采集链**自身**的漂移。成本 4 分钟/场次。
> 首尾两段若解析结果不一致,说明设备/固件/温度在场次内发生了变化,该场次数据需降级使用。

### 3.5 盲化

产出 GT 的人(掌握注入日志)与做专家标注的人**不应是同一人**。
专家标注时**不得看到注入日志**,否则 N2 的"专家分歧率"失去意义。

## 4. 🔴 注入日志 —— 标签的唯一来源

> **(a) 受控注入相对 (b)(c) 的全部优势,就在这份日志。日志的精度 = 标签的精度。**

### 4.1 格式

```yaml
session_id: 20260915-lab-A-s03
operator: <姓名>
clock_source: NTP <server>          # 必填
clock_sync_verified_at: 2026-09-15T09:02:11Z
apparatus: {attenuator: "<型号>", siggen: "<型号>", netem_host: "<主机>"}
fixed_config: {...}                 # §3.3 全部变量

injections:
  - seq: 1
    t_start: 2026-09-15T09:14:22.000Z    # 墙钟,毫秒精度
    t_end:   2026-09-15T09:14:27.500Z
    layer: RF                             # ⭐ = primary_attribution
    mechanism: coverage_hole
    params: {attenuation_db: 25, ramp_ms: 500, hold_ms: 5000}
    condition: A_only                     # sham | A_only | B_only | A_plus_B
    pair_id: null                         # T2 时填组合编号
    workload: streaming
    expected_symptom: rebuffer
    observed_symptom: rebuffer            # 现场目视,事后核对
    valid: true                           # 症状未复现则 false
```

### 4.2 🔴 对时是最大的单点风险

B2 已发现:**app 层事件表的 `Chip Time` 比无线层表整整差 5 小时**,
且两边时间戳**各自都"看起来正常",没有任何报错**。

⇒ **注入日志的墙钟与 trace 时钟的对齐关系,必须在试采时逐条验证一遍。**
验证方法:施加一个**极其显著、时间明确**的扰动(如 30 dB 阶跃),
在 XCAP 里找到它,记录 `注入墙钟 − trace 时间戳` 的偏差,**对三个时钟列分别记**。

⚠️ 若不验证:150 个标签集体错位,**而且不报错**,第 9 周才会发现。

## 5. 已有的混合数据怎么用

**提问**:已有数据可能是 mixed 的,能 split 或手动修改吗?

### 5.1 ✅ 可以:时间窗切分(推荐)

用 B3 的 detector battery(24 条现象)扫全 trace,找出**只有一个现象活跃**的时间窗。

```
detector battery 扫描 → 现象活跃区间图 → 取"恰好一个现象活跃"的窗口 → 伪单故障 case
```

⚠️ **诚实标注**:检不出 ≠ 不存在(T3 可观测性)。这类窗口一律标

```yaml
fault_multiplicity: single_detected     # 不是 single
detector_coverage: [d01,...,d24]        # 只对跑过的 detector 负责
```

### 5.2 ✅ 更好:不切数据,切问题(优先)

同一份混合 trace,**限定到某一个症状实例**发问。
成本更低、真实性完全保留,且直接用上 `answer_scope`。**多数情况下优于 §5.1。**

### 5.3 ⚠️ 手动修改:只做加法,不做减法

| 方向 | 判断 |
|---|---|
| **加法**(往干净母本注入) | ✅ **可以** —— 即 (c) 变异路线,容器层能力已 100% 验证,四次复现 + 三次阳性对照 25/25 |
| **减法**(从混合 trace 抹掉一个故障的痕迹) | 🔴 **不要做** |

**减法不可行的三个理由**:

1. 141 种 log code **只解开 3 种**,`14 01 ff` 类(占 38%)完全未解析 —— 无法定位"某个故障的全部痕迹"
2. 删包会**制造新的假象**:被删出来的空隙本身看起来就像丢包/中断
3. 抹掉的是**表象**,不是原因 —— 该故障在其它层留下的后果仍在,GT 反而更不可信

### 5.4 🔴 (c) 变异母本必须先验干净

**加法路线有一个隐藏陷阱**:往一条**本身已有潜伏故障**的 trace 注入,产出的是多故障数据,而标签只写了注入的那一个 —— **这正是 T1 implicit B 的完美复现。**

⇒ **规则:变异母本必须先过一遍 detector battery,且 sham 判定为干净,才可作母本。**

### 5.5 已有数据的定位

| 数据 | 用途 |
|---|---|
| 15 条 PING trace(`Ver=1.11`) | **T3 层素材** + (c) 的变异母本(需先验干净) + L1–L4 任务素材 |
| 另一批(`Ver=1.05`) | ⬜ **容器模型在其上从未验证** —— 验证前不得使用 |

## 7. 试采:4 小时,本月内必做

**25–35 小时是一场战役,8 周前置期只够打一次。先花 4 小时验通整条链。**

### 7.1 内容

```
3 workloads × 2 机制 × 3 重复          = 18 个 T1 case
1 组合(A+B)× 2 重复                    =  2 个 T2 case   ⭐ 关键
2 个负例 + 1 次 sham + 首尾 canary
```

⭐ **那 2 个 T2 case 是试采里最重要的部分** —— 它回答"A 和 B 同时注入时,后果还能不能分离"。
这个问题若答案是"不能",**整个 T1/T2/T3 分层设计要重做**,而现在改的成本是 4 小时。

### 7.2 试采要回答的七个问题

| # | 问题 | 不通的后果 |
|---|---|---|
| 1 | 副档能被 XCAP 解出 Transport 层吗? | A3 无解,Transport 层永久缺失 |
| 2 | 🔴 **注入日志墙钟能与 trace 时钟对齐吗?三个时钟列各差多少?** | 150 个标签集体错位,不报错 |
| 3 | 注入的故障在 XCAP 里**看得见吗**?在哪一层、哪个参数? | 注入了但不可观测 = 无效 case |
| 4 | **真实体量下 Model 重建要多久?** | A8 的 9–22 秒是小数据产物,不能写进论文 |
| 5 | 一个 case 能否端到端走完 GT 管线,产出结构化 GT? | 管线缺环 |
| 6 | 5 分钟间隔够吗?会不会仍然现象重叠? | T1 层不纯 |
| 7 | ⭐ **A+B 的后果能分离吗?交互项显著吗?** | T2 设计需重做 |

### 7.3 试采顺带产出

- **Model 展开系数**实测值(填 §2.3 的空)
- 每种 workload 的**实际 GB/h**(校正 §2.3 的估计)
- 三个时钟列相对注入墙钟的**偏差表**

## 11. 设备清单

> **用途**:排期前的采购/借用核对表。按"没有它会死什么"排序,不按价格。
> 价格是**量级**,仅供判断可行性。

### 11.0 ⭐ 四个硬门槛

**没有这四样,对应的整类故障直接消失,不是"降级"是"没有":**

| # | 设备 | 没有它就失去 | 后果 |
|---|---|---|---|
| **1** | **可编程步进衰减器** | F-01 覆盖 / F-05 切换 / F-06 乒乓 / F-07 RLF | 🔴 **RF 层与 RRC 层的根因全没** |
| **2** | **RF 屏蔽箱(或屏蔽室)** | 同上 —— **衰减器在无屏蔽环境下无效** | 🔴 见 §11.1 的说明 |
| **3** | **自建服务器**(工作负载的对端) | F-12 限速 / F-13 时延 / F-14 丢包 / F-15 服务端 | 🔴 **Transport 层的根因全没** |
| **4** | **diag 可访问的手机 + XCAL** | 一切 | 🔴 免谈 |

⇒ **只有 1+2+3+4 齐备,混淆矩阵才有 ≥3 层。缺 1 或 2,矩阵退化到 MAC+Transport 两层,基本报废。**
**SDR、信号源、负载 UE 都是加分项,不是门槛。**

---

### 11.1 RF 通路控制 🔴 **最关键**

| 项 | 规格要求 | 量级 | 备注 |
|---|---|---|---|
| **可编程步进衰减器** | ① **可程控**(USB / Ethernet / 串口)—— 手动旋钮不行,注入时刻必须由脚本打时间戳<br>② 步进 ≤1 dB<br>③ 范围 **0–60 dB 以上**(F-07 RLF 需要深衰减)<br>④ 频段覆盖实验用频段(sub-6:600 MHz–6 GHz)<br>⑤ **切换速度**要够快(F-01 的 ramp 是 500 ms 级) | $500–1.5k / 通道 | Mini-Circuits RUDAT/RCDAT 系列、Vaunix Lab Brick LDA 系列、JFW 均可 |
| **第二个衰减通道** | F-05/F-06 的 attenuator swap 需要**两路独立可控** | 同上 | 或买双通道型号 |
| RF 电缆 / 转接头 / 合路器 | 合路器用于注入干扰(F-02) | 百元级 | |

#### 🔴 一个容易被忽略的问题:怎么把手机的天线接进同轴通路?

**绝大多数商用手机没有射频测试口。** 三条路:

| 方案 | 说明 | 评价 |
|---|---|---|
| **屏蔽箱 + 耦合天线** | 手机放箱内,箱内一根耦合天线走同轴出来接衰减器 | ✅ **推荐,标准做法** |
| 直连测试口 | 只有工程样机 / 部分模块有 | ❌ 商用机基本没有 |
| 屏蔽室 + 室内小型基站 | 最灵活但成本最高 | 🟡 有就用 |

⚠️ **这就是为什么屏蔽箱和衰减器是绑在一起的硬门槛**:
**没有屏蔽,手机仍从空中收到信号,你在同轴上加的衰减根本不起作用。**

### 11.2 屏蔽 🔴

| 项 | 量级 | 备注 |
|---|---|---|
| **RF 屏蔽箱**(带耦合天线 + 同轴馈通) | $2–10k | 隔离度建议 ≥60 dB。**决定可重复性的关键** |
| 屏蔽室 | — | 有则更好,但屏蔽箱够用 |

### 11.3 干扰源(F-02)🟡 加分项

| 项 | 量级 | 备注 |
|---|---|---|
| 矢量信号发生器 | $20k+ | 最正规,但贵 |
| ⭐ **USRP 发噪声 / LTE 类波形** | ~$1–2k | **便宜得多,足够做受控干扰**;若已有 SDR 则零成本 |
| 第二台手机做上行 | 0 | 最粗糙,可控性差,但试采够用 |

### 11.4 基站侧 🟡 加分项(决定配置类根因)

| 项 | 量级 | 备注 |
|---|---|---|
| **USRP B210 / N310** | $1–3k | 配 srsRAN 或 OAI(软件免费) |
| **Amarisoft callbox** | $20–50k | 开箱即用,商业级 |
| **可写 SIM**(sysmoUSIM 等) | ~$10 / 张 | 让商用手机附着到自建网络。**必需** |

⭐ **关键认识:XCAP 读的是 UE 侧 diag,与对面是商用基站还是 SDR 无关。**
```
手机 → QC diag → .drm → XCAP     ← 这条链不关心网络是谁的
```
⇒ **整条工具链不用改。** 有 SDR 就能拿回 F-08 邻区漏配、F-10 调度、F-11 RLC/PDCP 定时器。

⚠️ **法规**:在授权频段发射需要屏蔽环境或牌照。**在屏蔽箱内做则无此问题** —— 又一个屏蔽箱的理由。

| 项 | 备注 |

### 11.8 对时 🔴 **标签精度的命根子**

| 项 | 备注 |
|---|---|
| **NTP 服务器**(注入控制机与采集 PC **同源**) | 毫秒级足够(注入间隔 5 min,标签要毫秒精度) |
| GPS/PPS 同步 | 有则更好,非必需 |

⚠️ B2 已发现 app 层与无线层的 `ChipTime` 差**整整 5 小时**且不报错。
**注入日志的墙钟与 trace 时钟的偏差必须在试采时逐条标定**(见 §7.2 第 2 问)。

### 11.9 注入控制自动化 ⭐ **强烈建议**

一台控制机跑一个脚本,**同时做三件事**:

```
① 驱动衰减器 / netem        ② 打墙钟时间戳        ③ 写 injection_log.yaml
```

⭐ **手工操作是标签误差的最大来源。** 人按秒表记"我大概在 09:14:22 拉的衰减",
误差几百毫秒起步,而故障本身可能只有 1–5 秒。**脚本化后误差进入毫秒级,且免费得到注入日志。**

静态优先(可重复性)。若行驶,需 GPS 与路线记录 —— 见 §3.3。
