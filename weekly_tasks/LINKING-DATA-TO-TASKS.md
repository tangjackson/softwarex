## 1. 现有数据能撑到哪一档

### 1.1 逐档判断

| 档 | 任务类 | Oracle 来源 | **现有数据够吗** | 理由 |
|---|---|---|---|---|
| **L1** | 检索定位 | 状态谓词 / 离线解析 | ✅ **完全够** | 任何 trace 都行。离线 parser 已 100% 布局解出,`MSG_FILTER` 可做逐 code 完整性判据 |
| **L2** | 计算测量 | 精确值 | ✅ **完全够** | 且 T5 已可完整演示(All vs 1Sec:最差 SINR −20.0 / −12.9) |
| **L3** | 配置构建 | 状态谓词 | ✅ **完全够** | 🆕 **这一档根本不依赖网络数据质量** —— 考的是"能不能把软件配成 X 状态" |
| **L4** | 对比 | 导出文件比对 | ✅ **够** | 两批数据的四条差异(XCAL 版本 / 容器 Ver / IMEI / 采样档)本身就是现成的对比素材 |
| **L5** | 调查(RCA) | rubric + 可核验证据 | 🔴 **取决于 §3 的测试** | 需要"有事发生"。见 §2 |

⇒ **任务阶梯 5 档里 4 档不受影响,而这 4 档承载全部 software-use 论证。**

### 1.2 逐贡献判断

| 贡献 | 现有数据 | 说明 |
|---|---|---|
| **主贡献:agent 架构(M1–M6)** | ✅ **完全不受影响** | 六个机制在 L1–L4 上就能完整消融。M1/M2/M3/M4/M6 与网络故障无关 |
| **N2:RCA GT 效度(方法论)** | ✅ **基本不受影响** | 这是关于"GT 有多难建"的贡献。**现有数据的贫乏本身就是证据** |
| **N1:层间混淆矩阵** | 🔴 **几乎确定不够** | 需要**根因分布在 ≥4 个层**。自然数据的根因分布是不受控的,且大概率集中在 RF |
| **N3:workload 相关的故障后果** | 🔴 **结构上不够** | 见 §1.3 |

### 1.3 🔴 N3 为什么结构上做不了 —— 即使有了 streaming 和 teleop 数据

N3 要的不是"有三种 workload 的数据",是 **同一个故障在不同 workload 下的后果对比**。

自然采集的 streaming 场次和 teleop 场次**经历的是不同的网络条件** ——
你无法说"这个差异来自 workload"还是"来自那天信号不同"。**配对不存在,对比就不成立。**

**唯一的替代路线:观察性配对分析(matched-pairs)**

```
在 streaming 数据里找 N 次切换 → 记录各自的 RSRP 剖面
在 teleop  数据里找 N 次切换 → 记录各自的 RSRP 剖面
按 RSRP 剖面相似度配对 → 比较 App 层后果
```

这是标准的观察性研究手段,**比受控注入弱但真实有效**。前提是:

> 🔴 **每种 workload 下都要有足够多的同类故障实例**(建议 ≥20 次/类)才能配对。
> **这正是 §3 的 T-01/T-02 要测的东西。**

## 2. 四条从"无标签数据"通往 L5 的路

现有数据没有注入标签。但**并非所有 L5 任务都需要注入标签**。四条路,难度递增:

### 路线 A — 协议确定性因果链 ✅ **最可靠,建议优先**

有些因果关系由**协议**决定,不需要经验标签:

| 因果对 | 为什么是确定的 | 证据在哪 |
|---|---|---|
| 切换 → 数据面 gap | 切换本身就有中断期 | 信令消息 + 数据面时间序列 |
| RLF → 全断 | 定义如此 | 信令 |
| TCP RTO → 停顿 | 协议行为 | 抓包(需副档) |
| 重建 → 长中断 | 定义如此 | 信令 |

**任务形态**:*"t 处这个 gap 是什么造成的?"* 答案 = *"t−ε 的切换"*,
**GT 来自协议而非注入日志**,且可由信令消息独立核验。

⚠️ **词汇表有限**(大约 5–8 类),但每一类都可靠,且在真实数据里**大量存在**。

### 路线 B — 证据链构造(L5a)⭐ **本项目最该做的一条**

**把 L5 拆成两半**:

| | 考什么 | 需要标签吗 |
|---|---|---|
| **L5a 证据链构造** | 跨层找齐并组装证据:"找出 t 前后各层发生了什么,按时间与层次组织" | 🟢 **不需要** —— 评分依据是**证据是否真实存在、是否对齐、是否完备** |
| **L5b 根因归因** | 在候选中判定主因 | 🔴 需要 |

⭐ **L5a 恰好考的是 RCA 里最难的那部分能力** —— 跨层证据的发现与对齐 ——
**而它可以完全从现有数据生成,oracle 是"这条证据在数据里能不能被验证"。**

这一档**几乎完美契合本项目的第一贡献**:它测的是 agent 能不能驱动软件把散落在七层、
多个视图、不同时钟基准下的证据找齐 —— **这是 software-use 能力,不是领域推理能力。**

> **建议:把 L5a 提升为独立一档,写进任务阶梯。** 它把"L5 做不了"这个风险从**全有全无**变成**分级降级**。

### 路线 C — 自然故障 + 专家标注(T3 级)🟡 **取决于数据里有没有事**

真实数据里自然发生的劣化事件,由专家标注根因。**这就是 C5 专家研究。**
产出 T3 级标签(不完备,答案形态是排序因素列表)。

🔴 **前提:数据里得真的有事发生。** 而现有迹象**不乐观**:

| 迹象 | 数值 |
|---|---|
| `Drpped_Total` 全库最大值 | **13** |
| `Status_PDU_Drop` | **全 0** |
| `Dropped_By_FlowControl` | **空表** |
| B3 的 24 条现象中有信号的 | **14 / 24** |
| Transport 层 | **只剩 ICMP 那一半** |

⇒ **这看起来像一批干净的实验室 ping 数据,不像有故障的现场数据。**
**§3 的 T-01 就是来定这件事的,它是全部 13 项测试里最重要的一项。**

### 路线 D — 加法变异(合成 T1 标签)✅ **可做,但词汇有限**

即 (c) 路线:干净母本 + 容器层变异。已有实验支撑(四次复现 + 阳性对照 25/25)。

⚠️ **能造的故障词汇 = 容器层可表达的 + 已解开 payload 的 code**:
- 不需要 payload:删包 / 重排 / 复制 / 截断 → **丢包、乱序、gap 类**
- 需要 payload:改 RSRP / 改 SINR / 改 PRB → **只有 3/141 个 code 解开了**

⇒ **D 能撑起 Transport/包级故障的 T1 层,撑不起 RF 侧因果。**
⚠️ **母本必须先过 detector battery 验证干净**,否则就是 implicit B 的完美复现。

> ### ⚠️ T-07 已重写 —— 原判断"packet 载荷必在边车文件里"证据不足
>
> A3 的实验是:注入 code 为 `0x11EC` 的记录 → 225 条被接受、索引表生成、按钮点亮,但 `Protocol` 全 `Unknown`。
> 这曾被读作"载荷不在 `.drm` 里"。**但有一个更简单的解释:我们注入的 payload 本身就不是真的 packet。**
> 容器层我们完全掌握,payload 是构造的 —— XCAP 接受容器、索引它,然后无法解析一段垃圾载荷,完全说得通。
> **`Protocol: Unknown` 是"载荷不在这里"和"载荷不合法"的共同后果,单靠它区分不开。**
>
> 而两个更简单的解释一个都没测过:① **diag mask 里根本没开 `0x11EC`/`0x11ED`**;
> ② **`Post_Para_Packet_Message_Analysis = 0`**(后处理是关的,即使有数据也不会填充分析树)。
>
> ⇒ **判决性实验(纯离线,~1 h,已有 283 MB/s 的 parser)**:
>
> | 扫描结果 | 结论 | 行动 |
> |---|---|---|
> | 两个 code **一次都没出现** | mask 里没开 → **采集端设置问题** | 本次采集在 mask 里加上这两个 code |
> | **出现了**,但 XCAP 显示不出来 | 后处理开关或解析问题 | 开 `Post_Para_Packet_Message_Analysis` 重建一次 Model(T-07b) |
> | 出现了,且开后处理就能解出 | ✅ **不需要边车,packet 走 `.drm`** | 无需额外采集配置 |
>
> **真正不可能在 `.drm` 里的只有**:PC 侧网卡抓包(对应 `Synchro Viewer` 要勾的 "Network adapter")、
> 应用侧埋点(播放器缓冲、teleop 控制环时序)、以及 mask 若只记截断包时的完整载荷。
> **Transport 层的 TCP 统计量与 IP 包本身,大概率不需要边车。**
>
> 🔴 **这个实验必须在配 XCAL 之前跑** —— 结果直接决定 mask 怎么设。
