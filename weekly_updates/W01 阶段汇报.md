## A3 Packet Message / Synchro Viewer —— 🟡

### DoD
查清 `Packet Message` 与 `Synchro Viewer (TCP Flow)` 为什么没有被激活,给出根因或可执行的排查路径。

### 做了什么 —— 一条完整的逆向 + 注入实验链

**① 先纠正了一个方法论错误,才找到真正的 log code。**

此前认为 packet 类目用的是 `0x1134` / `0x1144`(名字叫 "PPP Rx/Tx frames, Rm iface unframed")。
**这是从"名字字典"推出来的 —— 而名字字典是显示属性表,不是解析器的 code 表。**

改去读 `MsgProperty.dat` 的**树节点结构**,发现:
⭐ **XCAP 的 `Packet` 类目下 18 个协议叶子,全部挂着同一对 code:`0x11EC` / `0x11ED`。**

⚠️ 而 **`0x11EC` 和 `0x11ED` 都不在那份 1,361 条的名字字典里** ——
⇒ **「不在字典里 ⇒ 解析器不认识」这个推断方法本身是无效的。**

**② 用注入实验验证。** 做法:在真实 `.drm` 里插入构造的 diag 记录,重建 Model,看 XCAP 的反应。
记录格式已完全掌握:

```
[total_len 2B LE][75 ef][QC时间戳 8B LE][record_type 3B][inner_len 2B][log_code 2B][QC时间戳 8B][payload]
```

| 版本 | 做法 | 结果 |
|---|---|---|
| v1 | 35 条前缀变体挤在一起 | ❌ **结果不可分解** —— `Filter Index` 是稠密序号,携带不了身份信息 |
| v2 | 4 组前缀放在**分离的文件位置** + 阳性对照 | raw 0/50、p4 7/50、p8 28/50、p12 0/50,**对照 25/25** |
| **v3** | 换成真 code `0x11EC` | ⭐ **225 条全部被接受;`MBPacketIndexTable.dat` 生成;`Packet Message` 按钮点亮** |
| v4 | 12 种长度字段变体 | ❌ `Protocol` 仍全 `Unknown` |
| v5 | 造一个兄弟 `.drmp` 边车文件 | ❌ 同上 |

**③ 查清了 packet 载荷在哪。**
- `ConvertPPPFrame.exe` 的字符串里有**四个并行的 "logging file name" 字段**
- 帮助文档写明 `drm+drmmp`、`drm+drmw` 是**合并**关系
⇒ ⭐ **packet 载荷不在 `.drm` 里,在 `.drmp` / `.drmmp` / `.drmw` 边车文件中。**

**④ 找到了 Synchro Viewer 的真入口。**
不是主菜单,是 **Packet Message 右键菜单里的 `Range to Sync`** —— **它是灰的**。

**⑤ 顺带查清 XCAP 内嵌了 Wireshark**:`libwireshark.dll`(52 MB)、
`interface_wireshark.dll`(66 个 `le_*` 导出,含 `le_set_pkt_encap`、`le_decrypt_esp`)、
`plugins/3.2` 与 `plugins/3.6`、`airpcap.dll`、`ConvertToPCAP.exe`、`ConvertPPPFrame.exe`。

### 出来的是什么

| 候选原因 | 状态 |
|---|---|
| 数据本身不含真实 IP 抓包内容 | ✅ **已证实,且是主因** —— 载荷在边车文件里,我们的 `.drm` 没有副档 |
| 勾选项不是真正触发条件 | ❌ **已排除** —— 注入后按钮确实点亮,触发链是通的 |
| 需要额外步骤(如重启) | ❌ **已排除** —— 重启后仍灰 |
| 版本/授权不支持 | 🟡 **未排除**,但可能性下降(`Range to Sync` 菜单项**存在但灰**,不是缺失) |
| 🆕 **后处理开关没开** | ⬜ **本周新发现的候选,因果未验证** |

⭐ **同时得到两条可以直接进论文的现象**:
- **「被接受 ≠ 被理解」**:225 条注入记录 **100% 被接受**(进了索引、计入记录数),
  但**没有任何语义解析**(protocol/端口/IP 全空)

  但 `Protocol` 列全 `Unknown`,后台 `MBPacketIndexTable` 的 **28 个字段全为 −1**

  —— **Packet Message Analysis 的后处理一直是关的**。后处理没开,分析树本来就不会被填充。

## A4 采样率与分箱语义 —— ✅

### DoD
查清 11 档采样率是什么、分箱方法有哪些、事件/信令是否被采样。

### 做了什么

**① 11 档采样率 —— 真机下拉框逐字目视。**

> `All / 10ms / 100ms / 200ms / 500ms / 1Sec / 2Sec / 3Sec / 4Sec / 5Sec / 10Sec`

默认值是 `1Sec`,与官方文档 *"Default sampling interval is 1 sec"* 一致。
⚠️ 文档写的区间是 "5 sec ~ 10 ms",**而真机最大档是 10Sec** —— 文档表述与真机有出入。

**② 分箱方法 —— 真机下拉框 11 项,而帮助文件只写了 8 个。**

真机:`Average(Arithmetic) / Average(Linear) / Medium / Median / Maximum / Minimum /
First / Last / Sum / Count / Mode`
**帮助文件漏了 `Average` 的两个变体、`Sum`、`Count` 共三处。**

⚠️ **`Medium` ≠ `Median`** —— Medium 是"最接近平均值的原始值",Median 是"排序中间值"。
**名字差一个字母,语义完全不同。**

**③ 两份官方文档对 `Mode` 给出互相矛盾的定义,而真机实测显示两份都不完全对:**

| | 文档 A | 文档 B | **XCAP 实际** |
|---|---|---|---|
| **值**的规则 | 最频繁值 ✅ | 按时间取中心值 ❌ | **最频繁值** |
| **位置**的规则 | 最后一次出现 ❌ | center position ✅ | **8 次并列里的第 5 次** |

⇒ **一个 agent 无论读哪份文档都会答错一半。**

**④ 三档采样率实测对照(All / 100ms / 1Sec),建了 5 个对照 Model。**
得到两条硬判据:
- **`P10msec.dat` 存在 ⇒ 采样率 = All**;其余档一律 `P100msec.dat`,**不存在 `P1000msec.dat`**
- 主采样率比 1 秒细时,XCAP 额外生成一套 `*_1sec` 汇总表;主采样率就是 1 秒时不生成

**⑤ 事件/信令不被采样 —— 用真机数据坐实。**
4,274 条真实信令消息、覆盖完整 17 分钟 trace,算了全部 4,273 个相邻间隔:
**最小 8 微秒、最大 9.76 秒、中位数 25.585 毫秒,跨越 6 个数量级**。
对比同一段时间的 KPI 数据:**1,002 个间隔里 970 个恰好等于 1.000 秒**。
⇒ **信令是事件驱动、不规则到达的,不会被打到固定采样网格上。**

### 出来的是什么

⭐ **T5(配置决定真值)的第一个量化实例**:同一份数据换采样档,

| | All 档 | 1Sec 档 |
|---|---|---|
| 最差 SINR | **−20.0** | **−12.9** |
| 低于 −125 dBm 的时间占比 | **21.33%** | **17.00%** |

⇒ **"这条 trace 最差的 SINR 是多少"这个问题,没有唯一答案,取决于采样档。**

### ⬜ 残留
- ⬜ 只测了 All / 100ms / 1Sec **三档,中间八档未测**
- ⬜ `Mode` 的位置规则只有 1 个 bin 的观测,需换有移动轨迹的 trace 复现

## B1 diag parser + oracle 通路 —— ✅

### DoD
B1.1–B1.5:写出自己的 diag 解析器,接开源库,与 XCAP 对账,做覆盖率统计。

### 做了什么

**① `.drm` 容器格式完全解开 —— 而且不需要猜。**

```
每条记录 = [total_len 2B LE][75 ef][QC时间戳 8B][record_type 3B][记录体]
按 total_len 前进即可走到下一条,一次遍历全文件
record_type = 14 01 01  → QC diag log packet(占 58%)
              14 01 ff  → 另一类(占 38%,未研究)
```

实测吞吐 **283 MB/s**,**15.3 GB 全量遍历,0 次重同步**。

⚠️ 这里踩过一个坑:链的起点不在文件 0 偏移,需要先"锚定"。
最初只要求连走 30 条就认账,**结果每个文件都错认 offset 0**(文件头区域碰巧能凑够 30 条)。
现在要求**连走 2,000 条**才认。

**② XCAP 自己的 `.dat` 文件格式(RSF)解开了 —— 确定性求解,不是搜索。**

```
[0..2]   magic 'RSF'
[3..20]  头部:+9 列数+1、+11 记录数 nrec
[21..]   列定义区:[名字长度][名字][类型码][u][宽度][00]
[se..]   前导区:长度 = 91 × 列数 + 41
[ds..]   数据区:定长记录,紧贴文件尾
```

**判定方式是两条独立路径算同一个记录长度,要求精确相等**:
- 路径 A(schema):`reclen = Σ col_size(类型,宽度) + 2`
- 路径 B(几何):`reclen = (文件长度 − schema_end − 91×列数 − 41) / nrec`

⇒ **全库 9,581 个 `.dat`,布局解出率 100%,可读记录 4,287 万条。**
若列数、前导区公式、或任何一列的宽度算错了,路径 B 几乎不可能既整除又恰好等于路径 A。

⚠️ 最后 5 个解不出的表也解开了:**前导区每列的字节数不是常数 91,那类表是 127**。
⬜ **是什么决定 91/127,仍然未知**(头部版本字节两类完全相同)。

**③ 0xB087 / 0xB0A4 的包结构解开,与 XCAP 自己的聚合表全量对账。**

```
0xB0A4:  payload[0:4] Version   payload[4:8] num_rb
         第 i 个 RB 块 = payload[18 + i*122 …],块内 +14 = Num Data PDU Received
```

计数器是**累计值**,需要逐包差分,**递增记差值、递减记 0**。

**⇒ 3 条 trace × 2 个 log code,六项全部 0.00% 误差:**

| Model | oracle 总量 |
|---|---|
| `7182026-PING-M1-R5-S1-COMP` | **9,948** |
| `7182026-PING-M1-R2-S1` | **6,319** |
| `7182026-PING-M1-R3-S1` | **6,472** |

**④ 一条重要的自我更正。**
这个字段曾在 08-30 被判定"**已证伪**",09-01 又被证明是正确答案。
⚠️ **真正的毛病不是候选选错了,是验证方法不足以支撑证伪**:
- 当初只有 **4 个对照点**,而逐秒命中率约 51% —— **4 个点无法把 51% 与 0% 区分开**
- 而且**只取了 RB[2],漏掉 RB[0] 的流量**(RB[2] 只占总量的 90.2% / 82.2%)

⇒ **"证伪"这个强结论所需的样本量,不低于"证实"。**

**⑤ `Filter Index` 的语义查清了。**
`MSG_FILTER_*.dat` 里的 `Filter Index` = **0-based 的全局记录序号**,
对 `.drm` 里所有记录(含非 diag)按文件顺序计数,不是文件偏移

⇒ ⭐ **`MSG_FILTER` 的记录数可以直接当"我的解析器有没有漏包"的逐 code 判据**,

## B2 时钟基准 —— ✅

### DoD

### 做了什么

**① 确认"两个时钟列"客观存在。**
此前因为 GUI 导出只有一列 `TimeStamp`,曾判定"计划原文『两列对比』这个提法可能不成立"——
**这个判断是错的**。两列在 XCAP 落盘的 `.dat` 里:
**`TIME_STAMP` 与 `ChipTime` 是两个独立的列,591 张表同时含有。**
(字段名有 7 种写法,说明是不同解析模块各自命名的。)

**② QC 64 位时间戳的换算公式,与开源库交叉验证。**

```
milliseconds = (raw >> 16) × 1.25 + (raw & 0xFFFF) / 40960.0
epoch = 1980-01-06 00:00:00 UTC
```

**③ 🔴 但这里出过一个量纲 bug,污染了一整轮统计。**
公式里低 16 位那一项**曾被写成"秒"**。低 16 位是"距上一个 1/800 秒刻度的余量",
满量程 `0xFFFF/40960 = 1.6` —— **这个 1.6 的单位是毫秒**。
写成秒就把它放大了 1000 倍,给每个时间戳**额外加上 0~1.6 秒的锯齿**。

⚠️ **要害在于:这个加量随 raw 的低位变化,两个时间戳相减时不抵消。**
⇒ 单看一个时间戳只是"秒内小数不太对",**但所有"间隔 / 抖动 σ"类统计全被污染。**

**④ 三个时钟区制查清了。** 扫全库 269 张同时含两列的表,逐表算差值中位数:

| 区制 | 表数 | `ChipTime − TIME_STAMP` | 出现在 |
|---|---|---|---|
| **A** | 229 | **+18.45 s** | 四个 PING 数据集的无线层表 |
| **B** | 24 | **≈ 0** | 全在另一个数据集,全是 5G NR / 信令表 |
| **C** | **5** | **+18000.4 s = 精确 5 小时** | app 层的 Ping/Iperf 事件表 |

⭐ **要害:同名的 `Chip Time` 列,在 app 层事件表里比无线层表整整差 5 小时**
(= 采集地 7 月的 CDT = UTC−5);**而 `TIME_STAMP` 跨层一致。**
⇒ 这是"**列名相同 ≠ 语义相同**"的硬案例。


⚠️ **这个取值是规格给的,不是我用实测证据选的。**
我 08-31 曾单方面标过"定案",而且**违反了自己写下的前置条件**
("应该等 B2.1–B2.4 有统计结果之后再定");

**实测两个都是关的** ⇒ 0.00% 不是被它们制造出来的。
(边界:这两个键名带 GPS,严格说只覆盖 GPS 数据,`.dat` 里的 `TIME_STAMP` 是否也受影响文档没说。)

| `RSRP Filtering` | **关** | ⇒ 建模时没有按 RSRP 门限静默丢样本 |
| `Post_Para_Packet_Message_Analysis` | **0 = 关** | ⭐ **A3 的新候选原因** |
| 后处理开关总览 | **40 个里只有 2 个为 1**(都是 WCDMA,与我们无关) | 本机后处理基本全关 |

### 出来的是什么

**13 个测试:真机 13 passed / CI(无真机)11 passed + 2 skipped。**
那两个真机测试**把本周的实测值钉死了** —— 例如
`libwireshark == 3.2.3`(**不是**此前误记的 3.6.8)、`plugins_dirs == ["3.2","3.6"]`,
**以后若被别的版本悄悄替换,测试会红。**

### ⬜ 残留
- ⬜ **3 个配置键未定位**。其中一个是 `Sampling Method of Discontinuous Parameter` ——
  官方明写*"目前只对 **Ping** 生效"*,而**我们的数据 15/15 全是 ping**
  ⇒ **它对我们全部数据生效,而它的值仍然未知。**
- ⬜ **键名 → 行为的映射整体未验证**。`MicroTimeStamp=1 → 微秒` 有旁证;
  `ASN.1 ViewerMethod=0` **官方没给 0/1 与 OBJ/OSS 的映射**,故原样保留整数不做解释

## B6 版本漂移时间线 —— 🟡

### DoD
产出 `drift_timeline_v0.md`:XCAP 的版本演化对分析结果的影响。

### 做了什么

此前 B6 一直只写一句"卡在 Accuver 知识库要登录"。
**但本机的版本证据从来没系统榨过一遍。** 本周榨完:

**① ⭐ 分析端:一份安装 = 两个构建批次,而且同时装着两代 Wireshark。**

**最硬的证据(不依赖时间戳)**:插件目录按 Wireshark 主版本分目录,而**两套并存**:

```
plugins/3.2/{codecs 12, epan 24, wiretap 2}   共 38 个
plugins/3.6/{codecs  8, epan 12, wiretap 1}   共 21 个
```

两条通路各自的归属:

| 二进制 | 版本 | 归属 |
|---|---|---|
| `libwireshark.dll`(52 MB) | **3.2.3**(内部串 `wireshark-3.2.3`) | 3.2 代,**进程内** |
| `wsDecoder.exe` | 5.11.5.0 | 3.6 代,**独立进程,IPC** |
| `wsProtoDissect.dll` / `interface_wireshark.dll` / `glib-2.0-0.dll` | — | 3.6 代 |
| `ConvertToPCAP.exe` / `ConvertPPPFrame.exe` / `airpcap.dll` | — | 3.2 代 |

**旁证**:安装树 5,897 个文件的时间戳分成两批 ——
**2025-01-24(4,580 个)** 与 **2025-12-22(1,285 个)**,
且 `plugins/3.2` 100% 落在前者、`plugins/3.6` 100% 落在后者,**零交叉**。

⇒ ⭐ **"XCAP-M 5.33.0.15" 这个版本号不唯一确定一份二进制集合。**
两台版本号完全相同的机器,如果一台打过 2025-12-22 那个增量、另一台没有,
**packet 解析走的是不同代的 Wireshark**,结果可以不同,而版本号一模一样。
⇒ **环境指纹只记版本号是不够的。**

⚠️ **顺带就地更正一条过度声称**:此前写的「`libwireshark.dll` built on **3.6.8**」**是错的**。
当时是在二进制里搜到 `3.6.x` 串就认了,**那是插件 ABI 兼容串,不是构建版本**。
与"把名字字典当成解析器的 code 表"是**同一类推断错误**:
**在二进制里搜到一个串 ≠ 那个串描述的是这个对象本身。**

**② ⭐ 采集端:我们自己的两批数据不是同一条产线出来的。**

逐个读 16 个 `.drm` 的文件头:

| | **15 个 PING trace** | **另一批** |
|---|---|---|
| XCAL 产出版本 | **O5.1.8.0** | **O3.6.4.332** |
| **容器格式 `Ver=`** | **1.11** | **1.05** |
| 手机 IMEI | …9045(Galaxy S23) | …7170 |
| 采样档 | 1Sec | All |

**15/15 个 PING 文件完全一致。四条相互独立的差异。**
此前只知道采样档不同 ⇒ **"这两批数据不可直接比较"这个结论现在有四条独立证据。**

⚠️ **由此产生一条新风险**:我们的容器模型是在 **`Ver=1.11`** 上建立并验证的,
⬜ **在 `Ver=1.05` 上是否成立,从未验证** ⇒ **B1 的全部结论严格说只覆盖 `Ver=1.11`。**

**③ 找到厂商自己维护的唯一一份变更记录。**
安装根目录下有一份 898 B 的内部工程备忘(韩文),全文 10 行,最有价值的两条:

| 日期 | 内容 |
|---|---|
| **2018.09.27** | Wireshark 库 **2.2.3 → 2.6.1**,并**改为 IPC 方式调用** |
| **2018.10.04** | ⚠️ **因一个 WLAN 显示 bug,回滚 2.6.1 → 2.2.3** |

⇒ ⭐ **软件版本不是单调前进的** —— 这正是 drift timeline 最想要的那类事件,而且是厂商自己记的。
而 "改为 IPC 方式调用" 这条,**正好解释了 ① 里 `wsDecoder.exe` 独立进程的存在**。

**④ ⭐ 拿到第一份官方 release note**(O5.33.4.16,2025-05-29,用户从知识库下载)。

三条价值:

1. **版本阶梯凑出三级**:装着的 **5.33.0.15**(补丁包日期 2025-01-23)
   → 这份 note 的 **O5.33.4.16**(2025-05-29)→ Downloads 里未装的 **5.33.11.10**
   ⇒ **`5.33.x` 的第三位半年多从 0 走到 11**,迭代频率远高于此前假设
2. **它带 `Supported ICD version` 表**:5G Qualcomm = `FJ`、4G Qualcomm = `BE`、
   Samsung 8.07/9.05、Mediatek 2.5/3.8
   ⇒ ⭐ **ICD 版本直接决定 diag 包怎么解** —— 这正是 B1 卡过一轮的那个问题
   ("本机数据的 Version 字段与公开实现的版本对不上")**的答案形态**
3. 变更条目里有 *"Improved Packet Message Viewer open time"* 与多条 *"Added decoding of …"*
   ⇒ ⭐ **解析能力逐版本增加,同一份 `.drm`,新版本能解出旧版本解不出的字段**
   —— **这是 drift 对 benchmark 最致命的形态:oracle 会随版本变。**
