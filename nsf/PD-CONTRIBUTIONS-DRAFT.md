## Contributions

Wireless measurement datasets start as chipset diagnostic logs from drive tests; closed commercial software, a post-processor, turns them into key performance indicators (KPIs) such as SINR (signal quality) and handover counts. Decoding the logs is largely solved by open tools [21–23]; what the numbers mean is not. For AI this matters: a model trained on pooled corpora cannot tell a network effect from a processing choice. In our data, counting table rows instead of events turned 37 handover attempts into 2,151. On one trace, worst SINR is −20.0 dB at the tool's finest setting and −12.9 dB at its documented 1-second default, a fivefold gap in linear terms. Neither is wrong, since 1-second averages hide 10-ms dips, but none of five public releases whose top-level documentation we checked (three from our campaigns) records its full export configuration. Metrology calls this definitional uncertainty [1]. Existing corpora, this solicitation's focus [2], cannot simply add settings: exports are already averaged and documentation departs from behavior, so procedures must be measured by experiment and values re-derived where raw logs survive. All evidence comes from one build (XCAP-M 5.33.0.15, which post-processes XCAL logs) and our pilot data.

**C1. Value Passport.** For each exported parameter, setting and tool build, we measure the procedure once and link every value in that field to it: instrument, procedure (sampling grid, averaging rule, statistic, records per event), time base, blind spots (including choices 3GPP leaves "up to the UE implementation" [3]), sensitivity range, verification tier with how many values were checked of how many (C2), and date. For the SINR case the passport reads: 'All' setting, minimum, export time zone unrecorded, range −20.0 to −12.9 dB, provisional, 2026-09. The passport is a wireless-measurement profile of Croissant 1.1, which supports PROV-O provenance down to individual values [4, 5], so Croissant-aware pipelines can pool or refuse values by procedure. *New:* measured per-parameter procedure content for a closed post-processor, which we found nowhere: containers, registries and aggregation norms [4–9], tool-recording practice [10], known tool dependence [11, 12] and our test methods [13–15] exist, but releases state at most a dataset-level rule [34]. *Evidence (by hand):* the tool's declared rules cover 743 of 1,171 parameters (428 blank, meaning unknown); four documentation-behavior gaps bear on values (one seen in a single bin); export times sit 5 hours behind chipset time in two collections and match it in a third, recorded nowhere. *Deliverable:* the profile (to be proposed to the MLCommons Croissant working group), passports for every field of our XCAL-processed campaigns, and a dated per-build catalog of tool behavior, including what the tool changes on its own at each launch.

**C2. Two-Path Rule.** A value is *certified* only when a path avoiding both the vendor tool and any AI agent reproduces it; otherwise it is *provisional* (one path) or *unverified*. Independence is tested two ways: provenance tracing shows the paths share only the raw log bytes, with no decoder, intermediate file, code or model in common, and planted faults measure how often both fail together, since separately built versions can still fail together [16, 51]. Every step checks outputs, not exit codes: in a controlled test, five of seven export forms wrote 0 bytes while exiting normally. Fields drafted by C5 stay unverified until a certifying check passes; measured values are never agent-generated. *New:* tested disjointness with measured coincident failure, and per-value tiers for a commercial post-processor's KPIs, which we found in no wireless dataset; assumed independence fails in N-version experiments [16], and attestations, quality vocabularies, verified pipelines for other data and open decoders exist [17–23]. *Evidence:* our reader for XCAL's container (we found no public one) counts the same records as the tool for 165 of 167 log codes on one ping trace but decodes payloads for only 3 of at least 141, and its value matches have not passed the independence test, so no value is certified. Our 50-of-50 value agreement compares the export with the tool's own tables, after we caught a table family that merely mirrored the export, so it checks only the export step. *Plan and deliverable:* pair our container reader with open payload decoders [21–23], starting with the codes behind headline KPIs; release tier terms within the passport profile, a check library and the reader or, if legal review blocks it, the reader's test outputs.

**C3. WiReady.** WiReady, an auditor we will build (its checks are manual today), instantiates for wireless the solicitation's "automated platforms that discern the readiness of legacy datasets at scale" [2]. For each field it will return the procedures consistent with the export (sampling interval, averaging rule, clock offset, missing capture types, event-counting rule) at a stated coverage, or "not inferable", calibrated on our re-exports at known settings and tested on held-out campaigns; it will record this with tiers in Croissant's metadata and responsible-AI fields, and state limits such as "no application-layer throughput: packet capture was off." AI assistants and repositories can call it. We also test whether passports make an assistant state the setting its answer depends on, against a prompt-only baseline; if the prompt suffices, we report that passports add nothing here. *New:* per-field procedure inference for radio-KPI exports, with calibrated abstention, and a disclosure test for measurement data, which we found nowhere; signal forensics infers processing history from outputs in other domains [52]; readiness and FAIR checkers work at dataset level [24–26], and benchmarks score answer conditions in documents or task success [27–29]. *Evidence (pilot):* by hand we found packet capture off in 8 traces (3.3 GB), stated nowhere. An AI assistant working from a shell, mostly by reading the tool's model files, solved 5 of 11 tool tasks fully and 5 partly, yet none of its 5 numeric answers named its setting (one model family and grader; single seed; numeric ground truth awaits calibration). *Deliverable:* WiReady and RQ5–RQ6 evaluation materials from held traces re-exported at known settings.

**C4. Comparable existing corpora.** We apply C1–C3 first to our five published campaigns (2020–24; one joint with the Ghosh lab), whose raw logs we hold: Lumos5G [30], 5Gophers [31], 5G mobility [32], 5G mid-band [33] and Chicago/Minneapolis [34]. Two [33, 34] used XCAL, one [32] chipset-level logs and two [30, 31] phone-side app logs, which gives a cross-tool test within our corpus (XCAL first, the rest in Year 2). They hold [X TB] of raw logs ([32] alone spans 6,200+ km on three US carriers) and have been cited [N] times; enhanced releases will be hosted at [repository], with privacy (device IDs, GPS) under the Data Management Plan. Partner XCAL or Keysight Nemo corpora follow where letters of collaboration exist. Five parts: (1) re-derivation from raw logs under a stated procedure or, for export-only corpora, C3's procedure inference or a "not comparable" flag; (2) sensitivity ranges for headline KPIs; (3) after-the-fact radio-application alignment, each join stating its time bound; (4) a deduplicated event layer with published counting rules; (5) labels from application records, for models predicting application failures from radio data, with a label-error audit. *New:* open comparability with per-field provenance for existing radio-KPI corpora across groups and post-processors, which we found nowhere; closed tools re-derive other vendors' logs under one undisclosed procedure [35]; cross-tool comparisons [11, 12, 36] and each component method [22, 37–41] exist. *Evidence (pilot):* 602 video stalls and 73,714 frames recorded outside the tool; radio-application alignment within ±1.5 s for streaming and only seconds for teleoperation, comparable to the 2.0 s median stall, so stall labels hold only at second level. Nothing is harmonized yet; expert labeling has not started.

**C5. Recovery Engine (conditional).** *Why fundamental, and what is solved.* Operating closed software is solved: computer-use agents run professional and scientific-instrument software [29, 53], runtimes make their actions transactional [54], agents learn undocumented tools by experiment [44–46], and a shell-only model operated our tool (C3). What remains comes from the environment, not from model capability. The tool is its own only witness: an export can exit normally, write nothing and rewrite the whole model, and silent failures are reported for other scientific tools too [55]. Its procedures are written nowhere public (in 12 of 15 open-book runs the model reported finding nothing usable), every run rewrites the tool's state, and there is no cheap, observable reset. Hand work does not scale: our releases use [N_params] parameters, the full catalog has 12,881 parameter-setting cells per build and tool, and our own hand loop was misled three times. *What we must solve.* C5 is an AI system designed to recover procedures by experiment and hand every result to C2; it never certifies, and no second model substitutes [42, 43]. It builds on our prior software-use agent (manuscript in preparation; work in progress under other support, [source]), for which no support is requested, and adds four parts: an admission gateway that certifies a draft only through C2's human-reviewed, control-tested check, an authority split argued for agents [56, 57] that we extend to independence from the tool; a known-answer lab of synthetic containers, re-exports at known settings and planted false documentation claims; an experiment-validity test that counts a run only if its effect clears the tool's measured background churn; and a claim store that re-flags every dependent field when a claim is overturned [58, 59]. Three potential algorithms: A1 picks the setting, mode or trace segment that best separates candidate procedures per license-hour, updates only when paired controls read correctly, and may declare a rule non-identifiable; its classical criteria [60–62] and hidden-query recovery [63] assume cheap, side-effect-free queries. A2 screens which settings each value depends on [64]. A3 keeps a synthesized check only if it catches faults planted in re-derived values, shares no artifact with the checked path, and rarely fails together with it [51, 65]. *New*, as far as we found: metadata about a closed instrument admitted only through a path that shares nothing but raw log bytes with tool and agent; for A1–A3 only the application is new. *Gate.* C5 is judged by the metadata it produces (RQ9): certified rules per person-hour on a sealed reference, against an analyst with scripts and a no-engine agent with the same access, and admissions among at least 30 planted false claims (target 0). If either baseline matches it, or too few fields reach the certified tier to test, C5 is withdrawn: it stays a method under C1/C2, scripted sweeps fill C1 at smaller coverage, and C1–C4 stand. If a one-line "state your settings" prompt matches A2, A2 is dropped and the result is reported under RQ6. Today only the lab's synthetic containers and one measured churn footprint exist; the other parts are designed, and no agent has run this loop yet. *Deliverable:* per build, the fields C5 drafted and the tier each reached, then its dataset-scale code and checks (legal review permitting).

**What we do not claim.** No new format, decoding advance or discovery that KPIs depend on the tool [11, 12]; no single method (each has precedent, including every ingredient of C3 and C5 [51–65]; our claim is their combination, which we found applied nowhere to closed wireless post-processors); no cross-layer root-cause analysis [47]; no first AI-ready or labeled wireless dataset [48–50]; no agent that operates closed software, no general-purpose agent and no agent benchmark [29, 53]: C5 is judged only by the metadata it produces (RQ9, RQ10), its base is our prior work, and RQ6 evaluates our metadata, not models. The SINR case is aggregation arithmetic, not a vendor defect; 1-second data suit coverage and long-run throughput, not sub-second questions such as dips, stalls and handover interruptions. We collect no new measurements; all work re-derives, re-exports or audits logs already held. The pattern may transfer to other closed instrument software [15]; we claim no results outside wireless.
